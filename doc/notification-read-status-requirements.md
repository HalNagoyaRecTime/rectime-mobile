# 通知既読・未読機能 要件定義書

## 1. 概要

本機能は、モバイルアプリ利用者が自身に届いた通知の既読・未読状態を確認し、通知を個別または一括で既読にできる機能である。

通知の既読状態はバックエンド DB で管理し、モバイルアプリは通知一覧、通知ベル、未読件数表示に利用する。管理画面では利用者ごとの既読状態を参照できるが、既読状態の変更は行わない。

## 2. 目的

- ユーザーが未確認の通知をすぐ把握できるようにする
- 通知一覧で既読通知と未読通知を区別できるようにする
- 確認済みの通知を既読化し、通知ベルや未読件数を整理できるようにする
- FCM 通知の受信状況に依存せず、DB 上の通知状態を正として扱えるようにする
- 他ユーザーの通知を参照、既読化できないようにする

## 3. 対象ユーザー

### 3.1 モバイルアプリ利用者

- 自身の通知一覧を確認する
- 未読件数を確認する
- 通知を個別または一括で既読にする

### 3.2 管理画面利用者

- 通知ごとの送信結果を確認する
- 対象ユーザーごとの既読状態、既読日時を参照する
- 既読状態の変更は行わない

## 4. 機能要件

### 4.1 既読状態の保持

- バックエンドは通知ごとに既読状態を保持できる
- バックエンドは通知ごとに既読日時を保持できる
- 新規作成された通知は未読状態で保存する
- 既読状態は `read_at` から判定する
- `read_at` が `NULL` の通知を未読とする
- `read_at` に日時が入っている通知を既読とする
- `is_read` をレスポンスに含める場合は、`read_at IS NOT NULL` から算出する
- 一度設定された `read_at` は通常操作では更新しない

### 4.2 通知一覧での既読・未読表示

- モバイルアプリはログインユーザー自身の通知一覧を取得できる
- 通知一覧では各通知の既読・未読状態を表示する
- 未読通知と既読通知は視覚的に区別できるようにする
- 通知一覧 API は `read_status` による絞り込みに対応する
- `read_status` は `all`、`read`、`unread` を指定できる
- `read_status` 省略時は `all` として扱う

### 4.3 未読件数

- モバイルアプリはログインユーザー自身の未読通知件数を取得できる
- 未読件数は `read_at IS NULL` の通知のみを集計する
- 他ユーザー宛の通知は未読件数に含めない
- 通知ベルには未読通知の有無を表示する
- 未読件数を表示できる場合は通知ベルに件数を表示する

### 4.4 個別既読化

- モバイルアプリは指定した通知を既読にできる
- 対象通知がログインユーザー自身の通知である場合のみ既読化できる
- 対象通知が未読の場合、サーバー時刻で `read_at` を設定する
- 対象通知が既読済みの場合、既存の `read_at` を維持して正常終了する
- 既読済み通知に対して再度既読化 API が呼ばれてもエラーにしない
- 他ユーザー宛の通知は既読化できない

### 4.5 一括既読化

- モバイルアプリはログインユーザー自身の未読通知を一括で既読にできる
- 一括既読の対象はログインユーザー自身の未読通知のみとする
- 既読済み通知の `read_at` は更新しない
- 一括既読 API は処理件数をレスポンスに含める
- 他ユーザー宛の通知は一括既読の対象に含めない

## 5. API 要件

### 5.1 GET `/api/v1/notifications`

ログインユーザーの通知一覧を取得する。

主なクエリパラメータ:

| パラメータ | 必須 | 説明 |
| --- | --- | --- |
| `read_status` | 任意 | `all` / `read` / `unread`。省略時は `all` |
| `limit` | 任意 | 取得件数。省略時は 20、最大 100 |
| `offset` | 任意 | 取得開始位置。省略時は 0 |

主なレスポンス項目:

- `notification_id`
- `type`
- `title`
- `message`
- `link_url`
- `severity`
- `is_read`
- `read_at`
- `created_at`
- `sent_at`

### 5.2 GET `/api/v1/notifications/unread-count`

ログインユーザーの未読通知件数を取得する。

レスポンス例:

```json
{
  "unread_count": 3
}
```

### 5.3 PATCH `/api/v1/notifications/{id}/read`

指定した通知を既読にする。

レスポンス例:

```json
{
  "notification_id": "123",
  "is_read": true,
  "read_at": "2026-06-17T10:00:00+09:00"
}
```

### 5.4 PATCH `/api/v1/notifications/read-all`

ログインユーザー自身の未読通知をすべて既読にする。

レスポンス例:

```json
{
  "updated_count": 3,
  "read_at": "2026-06-17T10:00:00+09:00"
}
```

## 6. エラー要件

| ステータス | ケース |
| --- | --- |
| 401 | 未認証 |
| 403 | 他ユーザー宛通知への操作 |
| 404 | 通知が存在しない、または自身が参照できない通知 |
| 400 | 不正なクエリパラメータ |

## 7. データ要件

通知テーブルでは以下の項目を既読・未読管理に利用する。

| カラム | 説明 |
| --- | --- |
| `user_id` | 通知対象ユーザー ID |
| `read_at` | 既読日時。未読の場合は `NULL` |
| `created_at` | 通知作成日時 |
| `sent_at` | 通知送信日時 |
| `send_status` | 送信状態 |

既読状態は原則 `read_at` から算出する。`is_read` を物理カラムとして保持する場合は、`read_at` と不整合が起きないよう更新処理を一元化する。

## 8. 受け入れ条件

- 新規通知が作成された時点では未読として扱われる
- 通知一覧 API のレスポンスで既読状態と既読日時を確認できる
- 未読件数 API でログインユーザー自身の未読通知件数を取得できる
- 個別既読 API を実行すると対象通知の `read_at` が設定される
- 個別既読後、未読件数が減る
- 既読済み通知に個別既読 API を実行してもエラーにならない
- 既読済み通知の `read_at` は再度更新されない
- 一括既読 API を実行するとログインユーザー自身の未読通知のみが既読になる
- 他ユーザー宛の通知は一覧取得、個別既読、一括既読の対象にならない
- 管理画面では通知ごとの既読状態と既読日時を参照できる
- 管理画面から既読状態は変更できない
